# Hardware and software resources

## Local operating plan

The target is Windows on a four-core i5-6300HQ with 16 GB installed RAM and a 2 GB GTX 960M. The baseline uses CPU-only execution. Start with two compute threads, one query at a time, and embedding and reranking batches of eight. Measure available RAM before loading, cap context at 4,096 tokens, and run embedding, reranking, and generation in separate sequential stages for batch experiments. Interactive inference should avoid keeping both the reranker and generator resident if the combined working set exceeds the budget.

| Item | Planning assumption and gate |
| --- | --- |
| Dense index | At 20,000–60,000 chunks and 384 float32 dimensions, vectors use about 31–92 MB before metadata. A memory-mapped array lets the runner avoid extra copies. Actual chunk count comes from ingestion. |
| Disk | Allow 10 GB free for one Windows CPU environment, cached model files, source and processed data, indexes, and experiment artifacts. This is a planning allowance. Record actual bytes in Phase 2 and keep one weight format per model. |
| Memory | Initial pilot target is at most 3 GiB incremental working set per active stage, with at least 2 GiB available system memory during execution and no sustained paging. Reduce batch or unload the previous stage if the pilot exceeds the target. Measure the UI separately with the app and backend active. |
| Index build | At a hypothetical 5–20 chunks/sec, 20,000–60,000 chunks take roughly 17 minutes to 3.3 hours for embedding. Pilot on 500 passages and project from observed throughput. Checkpoint completed embedding shards and reuse them across matching conditions. |
| Reranking | Score at most 20 pairs per query. Time a 30-query pilot and project validation and test runtime before launching them. Budget up to four hours per full retrieval pass initially and checkpoint per query. |
| Generation | Begin with 20 local validation questions. The planned held-out grid is up to 600 main generations before robustness variants. At an assumed 30–120 seconds each that is 5–20 hours, excluding review. Target up to 20 hours of resumable local batch inference. If the pilot exceeds this budget, use the same GGUF and runtime on available free compute or revise the frozen design before viewing test outputs. |
| Human review | Start with 40–60 questions. At an assumed 2–4 minutes per output, two paired outputs per question would take roughly 3–8 hours before calibration or any duplicate review. Time the review pilot and freeze the subset before reading held-out outputs. |

## Model choices

| Stage | Proposed choice | Alternative and trade-off |
| --- | --- | --- |
| Embedding | **BAAI/bge-small-en-v1.5**, MIT, 384 dimensions, English, with a 512-token input limit. Use the documented retrieval query prefix and normalized vectors. FP32 weights alone are roughly 130 MB using about 33M parameters. [Model card](https://huggingface.co/BAAI/bge-small-en-v1.5) | **all-MiniLM-L6-v2**, Apache-2.0, 384 dimensions, smaller weights and a default 256 wordpiece truncation. Use only as a validation fallback if BGE throughput is inadequate, then freeze the choice. [Model card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) |
| Reranking | **ms-marco-MiniLM-L6-v2**, Apache-2.0, a small English cross-encoder trained on passage ranking. Around 90 MB of FP32 weights at roughly 23M parameters. Its transfer to NLP papers is empirical. Set pair truncation explicitly and log its frequency. [Model card](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L6-v2) | Use the L2 variant as a dev-only latency fallback, with quality compared at the same candidate depth. [Model card](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L2-v2) |
| Generation | **Qwen2.5-1.5B-Instruct**, Apache-2.0, official Q4_K_M GGUF, around 1–1.2 GB of weights on disk plus context cache and runtime overhead. Feasibility and citation reliability require local piloting. Freeze GGUF hash, prompt template, runtime build, and decoding. [Official GGUF](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF) | **Qwen2.5-7B-Instruct**, Apache-2.0, several GB of Q4 weights and greater runtime requirements. Optional separate study on free Colab if available. Model size alone provides no evidence of stronger grounded performance. [Official GGUF](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-GGUF) |

## Framework choices and offline operation

The [Phase 5 held-out run](phase5.md) indexed 1,925 chunks across 40 papers. It took 7.44 minutes across measured stages and peaked at 412.3 MiB process working set. The vector cache occupied 2.96 MB. Checkpoint replay reused 312 base and 312 reranked results without loading models.

The Phase 4 Qwen Q4_K_M pilot ran on the laptop CPU at 15.01 median decode tokens/s and peaked at 1.76 GiB server working set. It abstained on all six reference-evidence questions, so downstream comparison remains gated on grounding behavior. See the [Phase 4 pilot report](phase4.md).

- Use Python, pytest, NumPy and rank-bm25 for the core. Exact NumPy search keeps the baseline simple and auditable on Windows. FAISS IndexFlatIP is an exact alternative if local latency justifies another dependency. Approximate indexes would add a separate recall trade-off and are outside the core scope. [rank-bm25](https://github.com/dorianbrown/rank_bm25) · [FAISS exact search](https://github.com/facebookresearch/faiss/wiki/Getting-started)
- Phase 2 uses the official BGE ONNX export with ONNX Runtime's CPU provider. Phase 3 uses the official AVX2 quantized MiniLM ONNX export with the same provider. Both pin model and tokenizer hashes. See the measured CPU costs in the [Phase 3 report](phase3.md). [BGE model card](https://huggingface.co/BAAI/bge-small-en-v1.5) · [MiniLM ONNX exports](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L6-v2/tree/233902d25c440f23af6f7d6e94d2946bac0bee0a/onnx)
- Use llama.cpp for local GGUF inference. Transformers is an alternative for GPU-based experimentation with original weights, which would require separate provenance and timing. Keep plain Python interfaces and SQLite artifact storage, with Streamlit consuming the same artifacts as the CLI. [llama.cpp](https://github.com/ggml-org/llama.cpp) · [Qwen runtime documentation](https://qwen.readthedocs.io/en/v2.5/run_locally/llama.cpp.html)
- After approval to begin implementation, pin Python, Windows CPU dependencies and runtime binaries, and cache only the selected dataset and weight files. Verify hashes and test with networking disabled and model loaders pointed at local paths. Use CPU as the reference runtime. Optional Colab runs use public inputs, per-question checkpoints and frequent exports to durable storage, with backend and hardware recorded. Free GPU access and session length vary. The default incremental service budget is **$0**, with no keys or billable resources required. [Colab FAQ](https://research.google.com/colaboratory/intl/en-GB/faq.html)
